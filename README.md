# ДомАкт: приёмка актов работ по МКД в MAX

## Назначение

Бот в мессенджере MAX для приёмки актов работ по содержанию и ремонту
многоквартирного дома (форма акта по приказу Минстроя № 761/пр, порядок
приёмки по приказу № 318/пр). Председатель совета МКД получает акт от
управляющей компании, собирает замечания жителей, LLM формализует их в
юридический черновик, и председатель либо подписывает акт, либо формирует
мотивированный отказ. Всё в нормативный срок 10/30 дней, без привлечения
юриста.

## Доступ к решению в MAX

- Бот: https://max.ru/t40_hakaton_max_bot
- Мини-приложение открывается кнопкой из бота (работает только внутри MAX).

Основной сценарий проверяется в развёрнутом боте: он подключён к боевому
бэкенду (`https://37-252-21-79.sslip.io`), на который указывает
мини-приложение. Локальный запуск через Docker (ниже) нужен для
воспроизводимой сборки.

### Используемые возможности MAX

- **Бот + мини-приложение в связке.** Бот ведёт процесс и присылает
  уведомления и PDF в чат, мини-приложение даёт чек-лист по позициям акта.
- **Диплинк `startapp`.** Кнопка из бота открывает мини-приложение сразу на
  нужном акте (`?startapp=<actId>`), без поиска и навигации.
- **Нативная навигация.** Системная кнопка «Назад» MAX (`BackButton`) внутри
  мини-приложения.

## Основной пользовательский сценарий

1. Управляющая компания присылает председателю PDF акта проделанных работ.
2. Председатель загружает его в бот.
3. Бэкенд проверяет форму акта и адрес дома, извлекает текст из PDF и
   распознаёт таблицу позиций работ через GigaChat.
4. Председатель подтверждает получение (фиксируется дата, от неё стартуют
   таймеры 10/30 дней) и открывает мини-приложение: жители дома получают уведомление о новом акте и все его позиции, после отмечают каждую как «ок» или «есть претензия» (претензия
   обязательно с фото).
5. Свободный текст замечания жителя формализуется GigaChat в юридическую
   формулировку.
6. Председатель просматривает агрегированную картину по всем позициям и
   принимает решение по каждой:
   - **Подписать акт.** В MVP это имитация подписания Госключом (заглушка,
     см. «Известные ограничения»): бот возвращает исходный файл акта от УК.
   - **Сформировать мотивированный отказ.** По спорным позициям с фото
     собирается черновик,
     председатель может его отредактировать, подтвердить и получить готовый
     PDF для отправки в УК.
7. Бот отслеживает срок 10/30 дней и напоминает о приближающемся дедлайне.

## Состав и архитектура

Монолитный Kotlin-бэкенд (Ktor) обслуживает одновременно вебхук бота MAX и
REST API для мини-приложения, отдельного сервиса под мини-апп нет.

![Архитектура бота приёмки актов МКД](docs/architecture-xl.svg)

Подпись акта Госключом в MVP не подключена (заглушка, см. «Известные
ограничения»).

- `backend/`: Kotlin/Ktor-приложение, Gradle-сборка, Exposed-доступ к
  Postgres, HTTP-клиенты MAX Bot API и GigaChat, PDF-рендеринг (OpenPDF).
- `webapp/`: статическое мини-приложение MAX (без сборки), хостится на
  GitHub Pages (деплой через `.github/workflows/pages.yml`), в docker-compose
  не входит.
- `deploy/setup.sh`: установка бэкенда на VPS и автообновление из `master`.
- `dev/update.sh`: отправка тестовых событий MAX (текст/кнопка/файл) на
  локальный или боевой бэкенд для сквозной проверки без реального MAX.

## Запуск через Docker

Нужны `docker` и `docker compose`. Одна команда поднимает Postgres и
бэкенд:

```bash
cp .env.example .env
# заполнить MAX_BOT_TOKEN и GIGACHAT_AUTH_KEY в .env (см. таблицу ниже)
docker compose up --build
```

Сборка занимает менее 5 минут (без учёта загрузки базовых образов). Проверка,
что бэкенд поднялся: `curl http://localhost:8080/health` → `ok <git-sha>`.

### Переменные окружения

Полный список с комментариями находится в [`.env.example`](.env.example).
Ключевые:

| Переменная | Назначение                                                                                                   | Обязательна |
|---|--------------------------------------------------------------------------------------------------------------|---|
| `MAX_BOT_TOKEN` | Токен бота MAX (выдают организаторы)                                                                         | да |
| `GIGACHAT_AUTH_KEY` | Authorization key GigaChat (developers.sber.ru)                                                              | да, для распознавания акта и формализации замечаний |
| `POSTGRES_PASSWORD` | Пароль БД для docker compose                                                                                 | да |
| `CORS_ORIGIN` | Origin мини-приложения на GitHub Pages                                                                       | да, для запросов из мини-аппа |
| `ADMIN_USER_IDS` | user_id операторов в MAX через запятую; пусто -> председатели подтверждаются автоматически (демо)            | нет |
| `DEMO_MODE` | Включает команду `/shift`, `/reset` и пометку «демо» в документах                                            | нет (по умолчанию `true`) |
| `DEV_AUTH` | Принимать заголовок `X-Dev-User-Id` вместо проверки `initData`, только для локальной отладки без MAX         | нет, **никогда `true` на проверке** |
| `PUBLIC_URL`, `WEBHOOK_SECRET` | Публичный адрес и секрет вебхука бота, пустой `PUBLIC_URL` -> long polling (подходит для локального запуска) | нет для локального запуска |

### Порты

- `8080`: HTTP backend (health-check, REST API мини-аппа, вебхук бота).
- Postgres (`5432`) наружу не публикуется, доступен только внутри
  docker-сети `db`.

### Зависимости

- Backend: Kotlin/Gradle, версии зафиксированы в `backend/build.gradle.kts` и
  `backend/gradle.lockfile`. Рантайм: `eclipse-temurin:21-jre` (см.
  `backend/Dockerfile`).
- Frontend: без сборки, ванильные HTML/JS/CSS в `webapp/`.

## Внешние сервисы и интеграции

- **MAX Bot API / Mini App** (`platform-api2.max.ru`): обязательная внешняя
  интеграция, без токена бота решение не запустить. В Docker не
  воспроизводится, для проверки сценария нужен рабочий бот в MAX.
- **GigaChat API** (`gigachat.devices.sberbank.ru`): распознавание таблицы
  позиций акта из текста PDF и формализация свободных замечаний жителей.
  Без `GIGACHAT_AUTH_KEY` эти шаги не выполняются (см. `enabled` в
  `GigaChatClient`).
- **Госключ**: в MVP не подключён, подписание акта сделано заглушкой (см.
  «Известные ограничения»).
- **Мини-приложение на GitHub Pages**: статический хостинг вне контейнера.
  Адрес бэкенда захардкожен в `webapp/config.js` (`window.API_BASE`) и
  указывает на развёрнутый backend, поэтому мини-приложение из MAX всегда
  работает с боевым сервером, а не с локальным контейнером.

## Данные

- Postgres (Exposed ORM): пользователи, дома, УК, председатели, акты,
  позиции акта, замечания, вложения, справочник правовых оснований,
  мотивированные отказы, журнал событий.
- Файлы (PDF актов/отказов, фото замечаний жителей) хранятся в локальном
  docker-volume `files`.

### Тестовые данные

При первом старте (пустая таблица домов) `Seed.kt` автоматически создаёт
демо-УК «ООО «УК Демо-Сервис»», демо-дом «г. Казань, ул.
Демонстрационная, д. 1» и справочник правовых оснований отказа
(`Grounds`). Эти данные нужны для основного сценария и создаются без
дополнительных действий.

При `DEMO_MODE=true` там же создаются демо-акты по этому дому, по одному в
каждом статусе: «Получен», «Идёт сбор замечаний», «Решение председателя»,
«Подписан», «Отказ направлен» (с готовым PDF мотивированного отказа) и
«Принят молчаливым согласием». В них есть отметки трёх демо-жителей и
претензии с приложенными фото. Фото нарисованы программно и подписаны
«ДЕМО-ФОТО», авторы и председатель в документах помечены «(демо)». Так
каждый экран можно посмотреть сразу после регистрации председателем, не
проходя сценарий несколько раз. Демо-жители не привязаны к MAX, бот им
ничего не отправляет.

Тестовые учётные записи в MAX создаются через обычный `/start` в боте:
выбор дома -> роль «Житель» или «Председатель совета дома» (см. «Пошаговый
сценарий проверки»). Если `ADMIN_USER_IDS` не задан, заявка председателя
подтверждается автоматически (демо-режим).

Пример акта для загрузки: [`demo/demo_act_1.pdf`](demo/demo_act_1.pdf)
(форма 761/пр, дом «г. Казань, ул. Демонстрационная, д. 1»; выбирайте его
при `/start`).

## Пошаговый сценарий проверки

Локально: `docker compose up --build`, дождаться `ok` на `/health`. Если
у бота настроен webhook на боевой сервер, локальный экземпляр с тем же
токеном в режиме long polling событий не получит. Для локальной проверки
нужен отдельный бот-токен либо эмуляция событий через `dev/update.sh`.

Сценарий в MAX (развёрнутый бот):

1. Открыть бота по ссылке из раздела «Доступ к решению в MAX».
2. В боте MAX: `/start` -> выбрать демо-дом -> роль «Председатель совета
   дома» -> указать ФИО и основание полномочий(вставить строку "протокол общего собрания № 5"). В списке актов дома сразу
   видны демо-акты во всех статусах.
3. Прислать боту PDF акта по форме 761/пр с адресом демо-дома
   (готовый пример: [`demo/demo_act_1.pdf`](demo/demo_act_1.pdf)). Бот подтверждает распознанные
   позиции. Если `GIGACHAT_AUTH_KEY` заполнен, позиции приходят
   автоматически распознанными из текста PDF.
4. Подтвердить дату получения акта, от неё стартуют таймеры 10/30 дней.
5. Открыть мини-приложение по кнопке из бота, утвердить распознанные позиции. 
6. Для первой позиции нажать "Есть претензия", описать претензию(что угодно про плохую уборку лестничных клеток) прикрепить
    [изображение](docs/pictures-for-complaints/dirty-stairs.png)
7. Для всех остальных пунктов указать, что претензий нет.
8. Перейти на вкладку "Решение" и завершить сбор замечаний.
9. Перейти к мотивированному отказу и нажать "Собрать черновик"
10. Проверить полученное возражение и формализированные жалобы жильцов. После сформировать Pdf.
11. Скачать полученный pdf файл.

Однако для полноценного тестирования необходимо одноверменно два аккаунта Max. 
Доходите до 2го пункта инструкции выше, после чего
1. Заходите с другого аккаунта в бота.
2.  В боте MAX: `/start` -> выбрать демо-дом -> роль «Житель»
3. Возвращаетесь на аккаунт, где председатель и выполняете пункты 3-6.
4. Возвращаетесь на аккаунт жителя и получаете уведомление о новом акте.
5. Заходите в него и по своему усмотрению указываете претензии или соглашаетесь с пунктами акта.
6. Возвращаетесь на аккаунт председателя и по своему усмотрению формируете мотивированный отказ, если предоставлены
релевантные жалобы или подписываете документ(в этом случае в чат загружается исходный файл, поскольку подпись на реализована в MVP)

Демо-команды бота (работают при `DEMO_MODE=true`, председатель видит их в
приветствии вместе со ссылкой на демо-акт):

- `/shift N`: сдвинуть дату получения текущего акта на N дней (1–40) в
  прошлое, чтобы без ожидания увидеть напоминания и таймеры 10/30 дней.
  Сдвиги суммируются; для акта с направленным отказом сдвигается дата
  отправки отказа (напоминание о новом акте).
- `/reset`: выйти из дома и начать сценарий заново; активный акт уходит в
  архив.

## Примеры ожидаемого поведения

- Фото или скриншот вместо PDF: бот просит прислать акт файлом PDF, акт не
  создаётся.
- PDF не по форме 761/пр: бот отвечает, что это не акт приёмки нужной формы,
  акт не создаётся.
- PDF, в котором не найден адрес своего дома: бот переспрашивает и
  принимает акт после подтверждения. Акт с адресом другого дома из
  справочника бот отклоняет («загрузить можно только акт по своему дому»).
- Претензия по позиции без фото: мини-апп не даёт отправить замечание, фото обязательно для любой оспариваемой позиции.
- После выбора дома и роли не позволит повторно их изменить, нажав на кнопки в предыдущих сообщениях.
- Попросит ввести дату ещё раз в случае, если был нарушен её формат при указании времени получения акта.

## Известные ограничения

- **Подписание акта сделано заглушкой.** Госключ не интегрирован; подписание
  в MVP помечается `stub=true` в журнале событий и не является
  квалифицированной электронной подписью (при `DEMO_MODE=true` PDF
  мотивированного отказа содержит демо-пометку).
- **Распознавание акта идёт по тексту, не по изображению.** Если PDF является
  сканом без текстового слоя, извлечение текста (OpenPDF) вернёт пусто и
  распознавание через GigaChat не сработает.
- **Фронтенд не контейнеризирован.** Он обслуживается GitHub Pages, адрес
  backend в `webapp/config.js` фиксированный (не читается из `.env`).
- **Справочник домов и УК смоделирован.** Интеграции с ГИС ЖКХ нет: дома,
  УК и справочник правовых оснований создаёт `Seed.kt` как демо-данные,
  полномочия председателя не сверяются с реестром (самозаявление,
  подтверждение оператором из `ADMIN_USER_IDS` или автоматически в демо).

## Остановка и повторный запуск

```bash
docker compose down          # остановить, данные (Postgres + файлы) сохраняются в volumes
docker compose up -d         # запустить снова с сохранёнными данными
docker compose down -v       # остановить и полностью очистить данные (pgdata, files)
```
