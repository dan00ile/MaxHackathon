# MaxHackathon: приёмка актов работ по МКД в MAX

## Назначение

Бот в мессенджере MAX для приёмки актов работ по содержанию и ремонту
многоквартирного дома (форма акта по приказу Минстроя № 761/пр, порядок
приёмки по приказу № 318/пр). Председатель совета МКД получает акт от
управляющей компании, собирает замечания жителей, LLM формализует их в
юридический черновик, и председатель либо подписывает акт, либо формирует
мотивированный отказ. Всё в нормативный срок 10/30 дней, без привлечения
юриста.

воспроизводимой сборки и проверки бэкенда через API.

## Основной пользовательский сценарий

1. Управляющая компания присылает председателю PDF акта прямо в чат бота.
2. Бэкенд проверяет форму акта и адрес дома, извлекает текст из PDF и
   распознаёт таблицу позиций работ через GigaChat.
3. Председатель подтверждает получение (фиксируется дата, от неё стартуют
   таймеры 10/30 дней) и открывает мини-приложение: там жители видят позиции
   акта и отмечают каждую как «ок» или «есть претензия» (претензия
   обязательно с фото).
4. Свободный текст замечания жителя формализуется GigaChat в юридическую
   формулировку.
5. Председатель просматривает агрегированную картину по всем позициям и
   принимает решение по каждой:
   - **Подписать акт.** В MVP это имитация подписания Госключом (заглушка,
     см. «Известные ограничения»).
   - **Сформировать мотивированный отказ.** По спорным позициям с фото
     собирается черновик (текст + правовые основания из справочника),
     председатель может его отредактировать, подтвердить и получить готовый
     PDF для отправки в УК.
6. Бот отслеживает срок 10/30 дней и напоминает о приближающемся дедлайне;
   после отправки отказа напоминает о новом акте.

## Состав и архитектура

Монолитный Kotlin-бэкенд (Ktor) обслуживает одновременно вебхук бота MAX и
REST API для мини-приложения; отдельного сервиса под мини-апп нет.

![Архитектура бота приёмки актов МКД](docs/architecture-xl.svg)

Подпись акта Госключом в MVP не подключена (заглушка, см. «Известные
ограничения»).

- `backend/`: Kotlin/Ktor-приложение, Gradle-сборка, Exposed-доступ к
  Postgres, HTTP-клиенты MAX Bot API и GigaChat, PDF-рендеринг (OpenPDF).
- `webapp/`: статическое мини-приложение MAX (без сборки), хостится на
  GitHub Pages (деплой через `.github/workflows/pages.yml`), в docker-compose
  не входит.
- `deploy/setup.sh`: установка бэкенда на VPS и автообновление из `master`.
- `dev/update.sh`: отправка тестовых событий MAX (текст/кнопка/файл) на
  локальный или боевой бэкенд для сквозной проверки без реального MAX.

## Запуск через Docker

Нужны `docker` и `docker compose`. Одна команда поднимает Postgres и
бэкенд:

```bash
cp .env.example .env
# заполнить MAX_BOT_TOKEN и GIGACHAT_AUTH_KEY в .env (см. таблицу ниже)
docker compose up --build
```

Сборка занимает менее 5 минут (без учёта загрузки базовых образов). Проверка,
что бэкенд поднялся: `curl http://localhost:8080/health` → `ok <git-sha>`.

### Переменные окружения

Полный список с комментариями находится в [`.env.example`](.env.example).
Ключевые:

| Переменная | Назначение | Обязательна |
|---|---|---|
| `MAX_BOT_TOKEN` | Токен бота MAX (выдают организаторы / `@MasterBot`) | да |
| `GIGACHAT_AUTH_KEY` | Authorization key GigaChat (developers.sber.ru) | да, для распознавания акта и формализации замечаний |
| `POSTGRES_PASSWORD` | Пароль БД для docker compose | да |
| `CORS_ORIGIN` | Origin мини-приложения на GitHub Pages | да, для запросов из мини-аппа |
| `ADMIN_USER_IDS` | user_id операторов в MAX через запятую; пусто → председатели подтверждаются автоматически (демо) | нет |
| `DEMO_MODE` | Включает команду `/shift` и пометку «демо» в документах | нет (по умолчанию `true`) |
| `DEV_AUTH` | Принимать заголовок `X-Dev-User-Id` вместо проверки `initData`, только для локальной отладки без MAX | нет, **никогда `true` на проверке** |
| `PUBLIC_URL`, `WEBHOOK_SECRET` | Публичный адрес и секрет вебхука бота; пустой `PUBLIC_URL` → long polling (подходит для локального запуска) | нет для локального запуска |

### Порты

- `8080`: HTTP backend (health-check, REST API мини-аппа, вебхук бота).
- Postgres (`5432`) наружу не публикуется, доступен только внутри
  docker-сети `db`.

### Зависимости

- Backend: Kotlin/Gradle, версии зафиксированы в `backend/build.gradle.kts` и
  `backend/gradle.lockfile`. Рантайм: `eclipse-temurin:21-jre` (см.
  `backend/Dockerfile`).
- Frontend: без сборки, ванильные HTML/JS/CSS в `webapp/`.

## Внешние сервисы и интеграции

- **MAX Bot API / Mini App** (`platform-api2.max.ru`): обязательная внешняя
  интеграция, без токена бота решение не запустить. В Docker не
  воспроизводится, для проверки сценария нужен рабочий бот в MAX.
- **GigaChat API** (`gigachat.devices.sberbank.ru`): распознавание таблицы
  позиций акта из текста PDF и формализация свободных замечаний жителей.
  Без `GIGACHAT_AUTH_KEY` эти шаги не выполняются (см. `enabled` в
  `GigaChatClient`).
- **Госключ**: в MVP не подключён, подписание акта сделано заглушкой (см.
  «Известные ограничения»).
- **Мини-приложение на GitHub Pages**: статический хостинг вне контейнера.
  Адрес бэкенда захардкожен в `webapp/config.js` (`window.API_BASE`) и
  указывает на развёрнутый backend, поэтому мини-приложение из MAX всегда
  работает с боевым сервером, а не с локальным контейнером. Это внешний
  сервис, который контейнеризировать не нужно (правило хакатона это
  допускает при условии, что условия проверки описаны, см.
  `docs/hackathon-brief.md`).

## Данные

- Postgres (Exposed ORM): пользователи, дома, УК, председатели, акты,
  позиции акта, замечания, вложения, справочник правовых оснований,
  мотивированные отказы, журнал событий.
- Файлы (PDF актов/отказов, фото замечаний жителей) хранятся в локальном
  docker-volume `files`; путь на хосте для проверки не нужен, доступ идёт
  через API.

### Тестовые данные

При первом старте (пустая таблица домов) `Seed.kt` автоматически создаёт
демо-УК «ООО «УК Демо-Сервис»», три демо-дома («г. Казань, ул.
Демонстрационная», дома 1, 2 и 3) и справочник правовых оснований отказа
(`Grounds`). Эти данные нужны для основного сценария и создаются без
дополнительных действий.

Тестовые учётные записи в MAX создаются через обычный `/start` в боте:
выбор дома → роль «Житель» или «Председатель совета дома» (см. «Пошаговый
сценарий проверки»). Если `ADMIN_USER_IDS` не задан, заявка председателя
подтверждается автоматически (демо-режим).

Пример акта для загрузки: [`demo/demo-act.pdf`](demo/demo-act.pdf)
(форма 761/пр, дом «г. Казань, ул. Демонстрационная, д. 1»; выбирайте его
при `/start`).

Для проверки без реального MAX-клиента: `DEV_AUTH=true` в `.env`, дальше
любой REST-запрос к `/api/...` можно авторизовать заголовком
`X-Dev-User-Id: <любое число>` вместо `X-Max-Init-Data`. Для эмуляции
событий чата (без мини-аппа) есть `dev/update.sh text|callback|file ...`
(см. комментарии в файле).

## Пошаговый сценарий проверки

Локально: `docker compose up --build`, дождаться `ok` на `/health`. Если
у бота настроен webhook на боевой сервер, локальный экземпляр с тем же
токеном в режиме long polling событий не получит. Для локальной проверки
нужен отдельный бот-токен либо эмуляция событий через `dev/update.sh`.

Сценарий в MAX (развёрнутый бот):

1. Открыть бота по ссылке из раздела «Доступ к решению в MAX».
2. В боте MAX: `/start` → выбрать демо-дом → роль «Председатель совета
   дома» → указать ФИО и основание полномочий.
3. Прислать боту PDF акта по форме 761/пр с адресом одного из демо-домов
   (готовый пример: `demo/demo-act.pdf`). Бот подтверждает распознанные
   позиции; если `GIGACHAT_AUTH_KEY` заполнен, позиции приходят
   автоматически распознанными из текста PDF.
4. Подтвердить дату получения акта, от неё стартуют таймеры 10/30 дней.
5. Открыть мини-приложение по кнопке из бота (или диплинком
   `https://max.ru/<bot>?startapp=<actId>`), от имени жителя (`/start` →
   тот же дом → роль «Житель») отметить хотя бы одну позицию как «есть
   претензия» с фото.
6. Вернуться в мини-апп председателем: увидеть агрегированную картину,
   выбрать «Сформировать отказ» и получить черновик с автоматически
   подставленными правовыми основаниями.
7. Подтвердить отказ: бот пришлёт готовый PDF мотивированного отказа в чат.

## Примеры ожидаемого поведения

- Фото или скриншот вместо PDF: бот просит прислать акт файлом PDF, акт не
  создаётся.
- PDF не по форме 761/пр: бот отвечает, что это не акт приёмки нужной формы,
  акт не создаётся.
- PDF с адресом другого демо-дома: бот отказывает («загрузить можно только
  акт по своему дому»). Если адрес своего дома в акте не найден, бот
  переспрашивает и принимает акт после подтверждения.
- Претензия по позиции без фото: мини-апп не даёт отправить замечание
  (FR-E5), фото обязательно для любой оспариваемой позиции.
- Отказ без хотя бы одной оспоренной позиции с фото: API вернёт
  `409 no_objections`, отказ не формируется.
- Отказ, который уже подтверждён (`confirmedAt` заполнен): повторное
  редактирование запрещено, API вернёт `409 refusal_confirmed`.

## Известные ограничения

- **Подписание акта сделано заглушкой.** Госключ не интегрирован; подписание
  в MVP помечается `stub=true` в журнале событий и не является
  квалифицированной электронной подписью (см. также демо-пометку в самих PDF
  при `DEMO_MODE=true`).
- **Распознавание акта идёт по тексту, не по изображению.** Если PDF является
  сканом без текстового слоя, извлечение текста (OpenPDF) вернёт пусто и
  распознавание через GigaChat не сработает; Vision/файловая загрузка в
  GigaChat реализована в клиенте, но не используется в этом пайплайне.
- **Фронтенд не контейнеризирован.** Он обслуживается GitHub Pages, адрес
  backend в `webapp/config.js` фиксированный (не читается из `.env`).
- Без `GIGACHAT_AUTH_KEY` акт всё равно принимается, но позиции не
  распознаются автоматически, а замечания не формализуются.

## Остановка и повторный запуск

```bash
docker compose down          # остановить, данные (Postgres + файлы) сохраняются в volumes
docker compose up -d         # запустить снова с сохранёнными данными
docker compose down -v       # остановить и полностью очистить данные (pgdata, files)
```
