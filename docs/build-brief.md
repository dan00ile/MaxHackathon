## Стек

- **Бэкенд — Kotlin.** Рекомендация: **Ktor** (не Spring Boot) — легче
  поднять за час, нативные корутины под асинхронные вызовы MAX Bot API/
  GigaChat, меньше boilerplate под 6-дневный спринт. Для доступа к БД —
  **Exposed** (JetBrains, лёгкая), а не полный JPA/Hibernate-стек.
- **Фронтенд — мини-приложение MAX (WebApp)**, статические HTML/JS/CSS
  (можно с React + [MAX UI](https://dev.max.ru/docs/webapps/bridge), но
  простой статический фронт быстрее для 6 дней), **хостится на GitHub
  Pages**. MAX явно разрешает GitHub Pages как хостинг мини-приложений
  ([dev.max.ru/docs/webapps/introduction](https://dev.max.ru/docs/webapps/introduction))
  — GitHub Pages сам даёт HTTPS на `*.github.io`, что и требует платформа.
  Плюс: не нужен отдельный сервер под статику, деплой — просто пуш в ветку
  `gh-pages`/`docs/`.
- **БД — Postgres** в Docker Compose (простое, предсказуемое, все Kotlin-
  ORM/query-библиотеки поддерживают из коробки).
- **Файлы (фото, PDF)** — для MVP локальный volume в Docker, не тащить S3/
  объектное хранилище ради хакатона.
- **LLM — GigaChat** (см. [requirements.md §7/§10](requirements.md)) —
  обычный чат для FR-E1, функция `table` для FR-B1.1.
- **PDF-рендеринг — обычная Java/Kotlin PDF-библиотека** (например
  OpenPDF/openhtmltopdf), не LLM (см. FR-G6 — LLM только формулирует текст,
  вёрстку собирает библиотека).

## Архитектура (текстовая схема)

```
MAX-платформа
  │
  ├─ Бот (webhook/long-polling) ──► Kotlin-бэкенд (Ktor)
  │                                     │
  ├─ Мини-приложение (GitHub Pages) ────┤  REST API бэкенда
  │   window.WebApp / MAX Bridge        │
  │                                     ├─ Postgres (Exposed)
  │                                     ├─ GigaChat API
  │                                     ├─ PDF-рендерер
  │                                     └─ Подпись: коннектор Госключа
  │                                        (Астрал/Диадок) или заглушка
```

Один Kotlin-бэкенд обслуживает и вебхуки бота, и REST для мини-приложения —
не разносить на разные сервисы ради хакатона (YAGNI/ponytail).

## Что в боте, что в мини-приложении

По рекомендации организаторов ([hackathon-brief.md](hackathon-brief.md#сценарии-работы-платформы-max)):
бот — для коротких действий/статусов/уведомлений, мини-приложение — для форм
со списками и сравнением. Разбивка по нашим FR ([requirements.md §4](requirements.md)):

| Где | Что | FR |
|---|---|---|
| **Бот (чат)** | Загрузка файла акта председателем; статус акта; обратный отсчёт 10/30 дней; проактивные уведомления; кнопки «Подписать» / «Сформировать отказ» (запуск действия) | FR-B1, FR-C2–C4, FR-F1–F3 |
| **Мини-приложение** | Просмотр/редактирование распознанных позиций акта; чек-лист «ок / есть претензия» по позиции с фото; сравнение позиций; просмотр агрегированной картины; редактирование черновика отказа перед подтверждением | FR-B1.1–B1.2, FR-D1–D5, FR-G1–G3 |

Мини-приложение открывается из бота диплинком
`https://max.ru/<botName>?startapp=<payload>` (payload — только латиница/
цифры/`_`/`-`, ≤512 символов, например id акта) — так бот передаёт контекст
(какой акт открыть) в мини-приложение.

## Интеграция с MAX: конкретика для разработчика

### Bot API

- Официального Kotlin SDK нет. Есть JS (`@maxhub/max-bot-api`) и Go. Для
  Kotlin — либо сгенерировать клиент из OpenAPI-спецификации MAX через
  генератор кода на dev.max.ru (тип Kotlin/Java поддерживается), либо
  написать тонкий HTTP-клиент на Ktor Client + kotlinx.serialization
  вручную поверх REST (это не большой объём — методы отправки сообщений/
  кнопок/файлов и приём апдейтов).
- Домен: `platform-api2.max.ru` (старый `platform-api.max.ru` устарел).
- Авторизация: токен бота в заголовке `Authorization` (не в query-параметре).
- События: `POST /subscriptions` (webhook) — предпочтительно для прод-режима
  в Docker; `GET /updates` (long polling) — проще для локальной разработки
  без публичного адреса.
- Регистрация бота: через `@MasterBot` в MAX, команда `/create`, ник
  оканчивается на `_bot`. Публикация — только для верифицированного
  юрлица РФ (для хакатона обычно выдаётся тестовый токен организаторами —
  см. [hackathon-brief.md](hackathon-brief.md)).

### Mini App (WebApp)

- Подключение скрипта в HTML мини-приложения:
  `<script src="https://st.max.ru/js/max-web-app.js"></script>` →
  глобальный `window.WebApp`.
- Обязательно вызвать `WebApp.ready()` после отрисовки экрана (убирает
  «скелетон» загрузки).
- Полезные методы: `WebApp.expand()`, `WebApp.close()`, `WebApp.openLink()`,
  `WebApp.BackButton.show()/.onClick()`, `WebApp.HapticFeedback`,
  `DeviceStorage` (локальное хранилище), QR-сканер, шеринг
  (`shareMaxContent`).
- URL мини-приложения (для настройки в боте): только HTTPS, ≤1024 символов,
  только латиница/цифры/точки/дефисы. `username.github.io/repo/...`
  подходит под это ограничение.

### Проверка личности пользователя (важно — источник частых багов)

- `window.WebApp.initDataUnsafe` — **нельзя** использовать как доказательство
  личности, это данные без проверки подлинности, доступные и подделываемые
  на клиенте.
- Настоящая проверка — `initData` (строка), проверяется на бэкенде:
  HMAC-SHA256 над строкой launch-параметров с использованием secret-ключа
  (из токена бота), результат в hex сравнивается с присланным `hash`.
  Алгоритм — [dev.max.ru/docs/webapps/validation](https://dev.max.ru/docs/webapps/validation).
- ⚠️ **Известный подводный камень** (подтверждён практикой на Habr): при
  сборке data-check-string по документации MAX «в лоб» алгоритм не
  совпадает с реальным поведением платформы — в некоторых реализациях
  рабочим оказывается литерал `WebAppData` (буква в букву как в Telegram
  Mini Apps), хотя в тексте документации MAX это не выделено явно. **Не
  доверяй описанию буквально — протестируй HMAC-проверку на реальных
  `initData` от тестового бота до того, как завязывать на неё логику
  ролей/председателя.**
- `user_id` для определения роли (FR-A1) брать **только** из
  провалидированного `initData`, никогда из тела запроса от клиента — иначе
  житель может представиться председателем.

## Структура Kotlin-бэкенда (рекомендация, не догма)

Монолит, без микросервисов — ради скорости. Модули по доменным зонам из
[requirements.md §4](requirements.md):

```
src/main/kotlin/
  routes/           # HTTP-роуты: бот-вебхук, REST для мини-аппы, health
  services/
    ActService       # FR-B — карточка акта, позиции
    TimerService      # FR-C — таймеры T0/T0+10/T0+30, планировщик уведомлений
    RemarkService      # FR-D/E — замечания, вызов GigaChat на формализацию
    SignatureFlowService # FR-F — подписание/заглушка Госключа
    RefusalService      # FR-G — сборка отказа (текст из LLM + PDF-рендер)
  integrations/
    MaxBotClient        # HTTP-клиент Bot API
    MaxInitDataValidator # HMAC-проверка initData
    GigaChatClient       # чат + функция table
    SignatureConnector    # Астрал/Диадок клиент или Stub-реализация
    PdfRenderer            # сборка PDF акта/отказа
  persistence/
    tables/...            # Exposed-таблицы: Пользователь, Дом, УК,
                           # Председатель, Акт, ПозицияАкта, Замечание,
                           # Вложение, Основание, МотивированныйОтказ, Событие
                           # (точные поля — requirements.md §6)
  Application.kt          # Ktor entrypoint
```

`TimerService` — планировщик таймеров должен работать независимо от
доставки уведомлений (NFR-5/FR-C5): не полагаться только на «отправили
уведомление → запомнили», а хранить контрольные даты в БД и опрашивать их
периодической корутиной (простой `while(true) { delay(...) ; checkDue() }`
или `kotlinx-coroutines` тикер — не нужен Quartz/отдельный джоб-раннер ради
хакатона).

## Docker и сдача

Точный чек-лист файлов — [hackathon-brief.md §«Формат сдачи»](hackathon-brief.md#формат-сдачи):
`Dockerfile` (Gradle build → JRE рантайм-образ) для бэкенда, `compose.yaml`
(бэкенд + Postgres), `.dockerignore`, `.env.example` без секретов,
`requirements.txt`-эквивалент для Kotlin — просто зафиксированные версии в
`build.gradle.kts`/`gradle.lockfile`, вменяемый README (пункты — см. бриф).
Сборка ≤5 минут.

**Фронтенд (GitHub Pages) не заходит в docker-compose** — это статический
хостинг вне контейнера. В README явно укажи это как внешний сервис, который
нельзя (и не нужно) воспроизвести в Docker — по правилам организаторов это
нормально, если условия проверки описаны (см.
[hackathon-brief.md](hackathon-brief.md#обязательно-для-всех-решений)).
